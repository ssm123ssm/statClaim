StatClaim tutorial

From a study description to a checked claim

Thirty-five short lessons. Each one adds a few ideas to the previous one, so work through them in order. By the end you can plan a study, analyse its data and know exactly which guarantees were checked.

Before you start

You need basic statistics: hypothesis tests, p-values, power. You do not need to know Lean or any programming language.

Open the repository in GitHub Codespaces, or install it locally with make setup (see the quickstart). Every lesson has a file in examples/tutorial/. Commands are shown as statclaim ...; from the repository folder, type uv run --locked statclaim ....

In VS Code the same two actions are StatClaim: Show Claims and StatClaim: Verify Current File, and mistakes are underlined as you type.

Lesson 1

Your first checked claim

In this lesson

We describe a simple two-group study, choose a test, and ask StatClaim to check one guarantee: that the test's false-positive rate is at most 5%.

A .stat file is a list of declarations. It contains no data and runs no analysis by itself. It states what the study is and which guarantee you want.

Reading the file

use ...
Loads a module of vocabulary. models.two_arm_binomial gives us the study model, sampling the design, and tests.fisher the test.
let name = ...
Names an object. Names cannot be reassigned. Arguments are always written name=value.
study
Two groups of 50 participants, each with a yes/no outcome.
design
fixed means the sample sizes are set before any data are seen.
null
The hypothesis being tested: both groups have the same success rate. Declaring a null does not say it is true.
analysis
Fisher's exact test at level 1/20. Numbers are exact, so write 1/20 or 0.05; both mean the same fraction.
claim
typeI(analysis) is the statement "if the null is true, this test rejects it with probability at most 1/20".
verification
verify asks the Lean proof checker to establish the claim.

Run it

There are two commands. compile checks the file and lists what would be verified. It is instant and proves nothing. check runs the verification.

statclaim compile examples/tutorial/01_first_claim.stat
statclaim check   examples/tutorial/01_first_claim.stat
verified [verification]: typeI(analysis)
  The specified two-sided Fisher analysis has Type I error at most 1/20
  under the null, for every common success probability in [0, 1].
  Assumptions:
    The samples follow two independent binomial distributions.
    Positive arm sizes were fixed before outcomes were observed.
    The error bound is under the null of equal success probabilities.
  Certificate: .statclaim/programs/.../request-001
Program status: verified

verified means Lean checked a proof of the claim. The assumptions listed under it are part of the result: the claim holds if they do. StatClaim cannot check that your real study was randomised properly or that participants are independent.

What you learned

  • A file declares a study, a null, an analysis and a claim.
  • compile inspects; check verifies.
  • A verified claim always comes with its assumptions.

Try it

Change alpha to 1/100 and run check again. The bound in the output follows your declaration.

Lesson 2

Reading a result

In this lesson

A verification is an object like any other. We pull out its status, its evidence and its assumptions by name, and we start writing shorter files.

Two things changed. First, constructors are nested: fixed(model=study) is written inside fisher(...) instead of being named. Use whichever reads better. Second, the last four lines read fields with a dot.

FieldValue after check
verification.statusverified
verification.evidenceThe checked claim and its certificate
verification.evidence.required_assumptionsThe three assumptions from lesson 1
analysis.alpha1/20

To see the values, ask for the full report:

statclaim check examples/tutorial/02_reading_results.stat --json

Evidence can be absent

evidence exists only after a successful verification. If verification fails or was never run, evidence is empty, and so is every field read from it. A file that merely compiles never has evidence.

Certificates. Each verified claim leaves a folder with the exact inputs, the Lean proof and a log. Anyone can replay it with statclaim check-certificate <folder>.

What you learned

  • Objects have named fields, read with a dot.
  • status says what happened; evidence exists only on success.
  • Certificates can be replayed.

Try it

Run compile --json on the same file. The fields are listed as not_executed: nothing has been proved yet.

Lesson 3

When StatClaim says no

In this lesson

We make two common mistakes on purpose and read the explanations. Knowing the two kinds of refusal is most of what you need to work with the tool.

Mistake 1: a question the test does not answer

Suppose the real question is whether the treatment improves the success rate by more than ten percentage points. We declare that null and keep the Fisher test.

03_wrong_null.stat:9:43: error [hypothesis_mismatch]: fisher: hypothesis contract mismatch.
Declared null: p_treatment - p_control = 1/10.
Supported null: p_treatment = p_control (equal arm success probabilities).
... replacing the null changes the statistical question.
Program status: invalid

invalid means the file itself is wrong and nothing can be verified. Fisher's test, as supported here, answers one question: are the two rates equal? The message does not tell you to switch to that null. Doing so would make the error go away by changing your question. Lesson 8 introduces a test that does support a margin.

Mistake 2: stopping when the result looks good

Now the null is fine, but the design is adaptive: the sample size depends on the data, for example by checking results as they come in.

03_optional_stopping.stat:7:1: obligation [sampling_scope]: analysis: data-dependent
stopping needs a justified sampling law before the fixed-sample guarantee can be used.
This is not evidence of inflated error.
unresolved_obligation [verification]: typeI(analysis)
Program status: unresolved_obligation

unresolved is different from invalid. The file is well formed, but the 5% guarantee was proved for a fixed sample size and nothing here shows it survives early stopping. StatClaim does not claim the error rate is inflated. It says the justification is missing. Lesson 10 shows how to plan an early stop properly.

StatusMeaning
verifiedLean checked the claim under the listed assumptions.
calculatedA number was computed. No proof (lesson 4).
unresolvedSomething needed for the claim is missing. Not a disproof.
invalidThe declarations do not fit together.

What you learned

  • Each analysis supports specific nulls and designs, and says which.
  • Invalid is a mistake in the file; unresolved is a missing justification.
  • Neither says anything about whether your hypothesis is true.

Try it

In the second file, change adaptive back to fixed and confirm the claim verifies.

Lesson 4

Analysing the data

In this lesson

The study has finished. We enter the counts, compute the exact p-value, and have Lean confirm the number and the decision.

observe
Attaches counts to an analysis. Counts outside the declared sample sizes are rejected when the file is compiled.
result(data)
The claim "this is the exact p-value and decision for these counts".
calculate
Computes the answer in exact arithmetic. Fast, and not a proof.
verify
Has Lean recompute the p-value from its own definition and compare.
calculated [calculation]: result(data)
  p-value = 1255807221238/58971773773923; decision = reject_null; no formal certificate issued.
verified [verification]: result(data)
  Exact p-value equals the Lean Fisher definition for these counts.
  Reported decision equals membership in the formal rejection event.
  The specified fixed-sample rule has Type I error at most 1/20 under the null model.
  Assumptions:
    ...
    The supplied counts describe the declared sampling procedure.

The p-value is an exact fraction, about 0.021. Results keep fractions; decimals are for display. Note the new assumption: Lean can check the arithmetic, but only you know whether these are the counts your study produced.

Calculate or verify? Use calculate while exploring. Use verify for anything you will report. The same split applies to every claim in the rest of this tutorial.

What you learned

  • observe attaches data; result is a claim about it.
  • calculate gives numbers, verify gives checked numbers.
  • Verifying a result adds the assumption that the counts are the real ones.

Try it

Change the treatment count to 18. The decision becomes do_not_reject_null, and it still verifies: a checked result is not the same as a significant one.

Lesson 5

Several endpoints

In this lesson

The study measures three outcomes. We split the 5% error budget between them so that the chance of any false positive stays at most 5%.

Testing each of three outcomes at 5% does not give a 5% study-wide error rate. The Bonferroni method gives each test a share of the budget.

Three analyses
Each endpoint is a Fisher analysis with its own level. The primary endpoint gets half the budget; the shares add up to exactly 1/20.
bonferroni
Groups the analyses into a family with an overall level. The list is written in square brackets.
joint_law
States what is assumed about how the outcomes relate. "binomial_marginals" assumes only that each outcome follows its own two-group model. The outcomes may be correlated in any way.
familywise
The claim: the probability of rejecting any true null is at most the overall level.
verified [verification]: familywise(endpoints)
  Strong familywise error is at most 1/20 under the declared marginal-law contracts,
  for every configuration of true and false endpoint nulls.
  The sum of the allocated endpoint levels does not exceed the familywise bound.

What you learned

  • A family groups analyses under one overall error level.
  • The shares must add up to no more than that level.
  • The guarantee holds however the endpoints are correlated.

Try it

Set all three levels to 1/20. You get an allocation obligation: the shares now add up to 3/20.

Lesson 6

Why it passed, and what a change affects

In this lesson

So far a valid file has been silent: no message means the pieces fit. We now ask StatClaim to show its reasoning, produce a report for the study file, and tell us what an edit affects.

When you write fisher(design=..., null=..., alpha=...), StatClaim checks that the pieces fit together. Lesson 3 showed what happens when they do not. When they do, the reasoning is kept and shown only if you ask. No new file is needed; we use the one from lesson 5.

statclaim explain examples/tutorial/05_several_endpoints.stat --name response
Conclusion: response: the design, the null and the level fit this analysis.

Why it passed
1. same-model: the null and the design describe the same study model.
2. supported-null: the declared null (p_treatment = p_control) is supported by this analysis.
3. level-range: the level 1/40 is a probability.
4. analysis-contract (from steps 1, 2, 3): the design, the null and the level fit this analysis.
5. fixed-sampling: sampling is fixed, as the fixed-sample error theorem requires.

Assumptions you must meet in the real study
- The two samples are independent, each with one common success probability.
- The arm sizes are fixed before outcomes are observed.
- The analysis and its level are chosen before outcomes are observed.

Unresolved obligations: None.
Not established here: No statistical guarantee is established here.
Independent check of this derivation: passed.

This is called a derivation. Read its parts separately:

PartMeaning
StepsEstablished from your declarations by a stated rule.
AssumptionsFacts about the real study. StatClaim cannot check them; you must.
Unresolved obligationsSomething a later guarantee needs that is not shown yet.
Not established hereA reminder: this is about fit, not about error rates.

A derivation says the declarations fit together. It is not the 5% guarantee; that is still the job of verify. The last line means a second, separate program re-read the declarations and confirmed every step.

In VS Code. Put the cursor on a declaration and run StatClaim: Explain Contract. Leave out --name on the command line to explain every declaration, including the family endpoints.

A report for the whole file

statclaim report examples/tutorial/05_several_endpoints.stat --output report.md

The report collects every derivation, the assumptions to meet, the open obligations and the claims the file requests. It is meant for a protocol appendix or a reviewer.

What does an edit affect?

A colleague suggests giving the two secondary endpoints more of the budget. The edited file changes two levels from 1/80 to 1/40:

statclaim impact examples/tutorial/05_several_endpoints.stat examples/tutorial/06_changed_levels.stat
Declarations
- remission: changed directly
- relapse: changed directly
- endpoints: affected through a dependency

Contracts affected
- remission: satisfied -> satisfied (re-derived for the new declaration)
- relapse: satisfied -> satisfied (re-derived for the new declaration)
- endpoints: satisfied -> satisfied, 1 unresolved

Claims affected
- verify familywise(endpoints): must be re-run: its subject changed

New diagnostics
- obligation [allocation] (line 17): endpoints: allocated alpha 3/40 exceeds the
  requested family bound 1/20.

Each analysis is still fine on its own. The family is where the edit bites: the shares now add up to 3/40, so the familywise claim has an open obligation, and the certificate from lesson 5 no longer describes this file. In VS Code, StatClaim: Show Change Impact does the same for your unsaved edits.

What you learned

  • A passing declaration keeps a derivation; you see it only when you ask.
  • Steps are established, assumptions are yours to meet, obligations are still open.
  • report documents a study file; impact shows what an edit affects.

Try it

Run statclaim explain on 03_optional_stopping.stat. The declaration passes its contract, with one unresolved obligation: the missing justification from lesson 3.

Lesson 7

Choosing a sample size

In this lesson

Before the study, we ask how many participants are needed to have an 80% chance of detecting the effect we expect.

Power depends on what you expect to happen. Those expectations are inputs you must supply. Here we expect a 10% success rate under control and 40% under treatment.

binomial_rates
The planning point: one expected rate per group. It is a guess for planning and does not replace the null.
power_target
What the design must achieve: power of at least 4/5 at the planning point, with a false-positive rate of at most 1/20.
meets
The claim "this analysis meets this target".
equal_arm_sizes
A range of designs to search, here 20 to 60 per group.
smallest_sample_size
The claim "some design in the range meets the target, and no smaller one does".
calculated [check]: meets(analysis)
  arm sizes = (25, 25); total = 50
  power ~ 0.5905; power target met = false; Type I target met = true
calculated [recommendation]: sample_size(candidates)
  arm sizes = (36, 36); total = 72
  power ~ 0.8004; power target met = true; Type I target met = true
verified [verification]: sample_size(candidates)
  Its power is at least 4/5 at p_control = 1/10, p_treatment = 2/5.
  No equal-arm candidate with 20 up to 35 controls reaches that power, so (36, 36)
  is the smallest sufficient candidate in the range 20 to 60.

Twenty-five per group gives only 59% power. The answer is 36 per group. Lean recomputes the power of that design and of every smaller one in the range.

What the result covers. Power is checked at your planning point only. If the true rates differ, the power differs. The "smallest" claim is about the range you declared, not about all possible designs.

For unequal groups, use allocated_arm_sizes with treatment_per_control=2 for two treated participants per control (examples/unequal_allocation.stat).

What you learned

  • Planning needs expected rates and a power target, both stated explicitly.
  • meets checks one design; smallest_sample_size searches a range.
  • Verified power is power at the planning point.

Try it

Raise the required power to 9/10. The recommendation grows; if it exceeds your range you get no_feasible_candidate, so widen the range.

Lesson 8

Better, or at least not worse

In this lesson

Most trials ask a directional question. We test whether a treatment is better than the control, estimate by how much, and then test whether a cheaper treatment is at least not much worse.

The Fisher test of lessons 1 to 7 asks whether two rates differ. Two more analyses ask directional questions. Both use a null you met in lesson 3, proportion_difference_at_most, and both reuse the claims and planning vocabulary you already know.

Is the treatment better?

no_better
The null "treatment rate minus control rate is at most 0": the treatment is no better. Rejecting it supports the treatment.
fisher_one_sided
The one-sided Fisher test. It accepts this null and no other. The level 1/40 is the usual one-sided 2.5%.

meets, observe and result are unchanged from lessons 4 and 7.

verified [planned]: meets(superiority)
  The one-sided Fisher analysis with arm sizes (36, 36) and alpha 1/40 has Type I error
  at most 1/40 whenever the treatment success probability is at most the control's.
  Its power is at least 4/5 at p_control = 1/10, p_treatment = 2/5.
verified [outcome]: result(data)
  Exact one-sided p-value equals the Lean definition for these counts.
  Reported decision follows from comparing that p-value with the level.

The one-sided p-value is 0.0065, so the null is rejected. Read the error claim closely: it holds whenever the treatment is no better than the control, including when it is worse. A guarantee only for exactly equal rates would be weaker.

By how much?

calculated [interval]: interval(study)
  control 4 of 36, treatment 14 of 36; estimate ~ 0.2778;
  interval = [-0.0691, 0.5627] at level 19/20

The estimated difference is 28 percentage points. The interval is built from an exact interval for each group, which makes it valid for every pair of true rates and also wide. Here it includes zero although the test rejected. That is not a contradiction: the interval is cautious, and the two answer slightly different questions. Report both.

Is it at least not much worse?

A cheaper treatment does not need to be better. It may be enough to show it is at most 10 percentage points worse. This is a non-inferiority question.

too_much_worse
The null "treatment rate minus control rate is at most -1/10": the treatment falls short by more than the margin. Rejecting it shows non-inferiority.
difference_test
An exact test for a null with a margin. It needs use tests.difference.
verified [trial_outcome]: result(trial_data)
  The exact difference test with arm sizes (60, 60) and the listed rejection thresholds
  has Type I error at most 1/40 whenever p_treatment - p_control <= -1/10.
  For 50 of 60 control and 52 of 60 treatment successes, the test does not reject the
  null: with that many control successes it needs at least 53 treatment successes.
calculated [chance]: meets(non_inferiority)
  arm sizes = (60, 60); total = 120
  power ~ 0.3017; power target met = false

The treatment did slightly better in the sample, and non-inferiority was still not shown. The last lines say why: with 60 per group this trial had only a 30% chance of succeeding even if the two treatments are equally good. Non-inferiority trials need large samples, and the planning step would have said so in advance.

What this test is. For each number of control successes, the test lists how many treatment successes are needed to reject. The list is stored in the certificate. Results are a decision without a p-value, and the test currently supports up to 120 participants per group.

What you learned

  • fisher_one_sided tests whether the treatment is better; difference_test tests a margin.
  • Their error guarantees cover the whole null, not only its boundary.
  • difference_interval estimates the difference, conservatively.

Try it

Search for a non-inferiority sample size: add equal_arm_sizes(analysis=non_inferiority, min_per_arm=60, max_per_arm=120) and calculate(sample_size(...)) with a target of minimum=1/2.

Lesson 9

A single-arm study

In this lesson

Everyone receives the treatment and we ask whether the response rate beats a known benchmark of 20%. We plan the study, analyse it, and report an interval.

This lesson uses a new test module but the planning vocabulary from lesson 7.

binomial_test
A one-sided exact test. The null is "the response rate is at most null_rate".
response_rate
The planning point for one group: we hope for 40%.
sample_sizes
The range to search, written inside the call this time.
verified [plan]: sample_size(<expression>)
  The exact binomial test with 35 participants, rejecting at 12 or more responses,
  rejects with probability at most 1/20 for every response rate at or below 1/5.
  It rejects with probability at least 4/5 at the response rate 2/5.
  No sample size from 10 up to 34 meets both bounds with this test, so 35 is the
  smallest sufficient candidate in the range 10 to 60.

So we recruit 35 and will declare success with 12 or more responders.

After the study

responses, binomial_result
The one-arm counterparts of observe and result from lesson 4.
confidence_interval
An exact interval for the response rate. level=19/20 is 95%.
verified [result]: result(data)
  The exact one-sided p-value for 14 responses out of 35 at the null rate 1/5 is
  approximately 0.005258.
  The test at level 1/20 rejects at 12 or more responses, so the decision is: reject the null.
calculated [estimate]: interval(study)
  14 responses out of 35; estimate ~ 0.4000; interval = [0.2387, 0.5789] at level 19/20
verified [coverage]: interval(study)
  For every true response rate, the exact confidence set for 35 participants contains
  that rate with probability at least 19/20.

The report writes itself: 14 of 35 responded (40%, 95% CI 24% to 58%), p = 0.005. The verified interval claim is about the method: whatever the true rate, intervals built this way contain it at least 95% of the time.

What you learned

  • tests.binomial covers testing and estimating one proportion.
  • Planning, testing and estimation share the same study declaration.
  • A confidence interval's guarantee is about the procedure, for every true rate.

Try it

Change the count to 10. The test no longer rejects, and the interval now includes 20%. The two results agree, as they should.

Lesson 10

Stopping early

In this lesson

We return to the problem from lesson 3 and solve it: a study with a planned interim look that stops early if the treatment is clearly not working.

Early stopping is fine when the rule is part of the design and the error rates are worked out for the whole procedure. A two-stage design does this: treat a first group, stop if too few respond, otherwise continue.

two_stage_binomial
Thirteen participants first, thirty more if the study continues.
threshold_rule
Continue only with more than 3 responders in stage one. At the end, reject the null with more than 12 responders in total.
two_stage_test
The complete design: stages, rule, and the benchmark rate it is tested against.

The target and meets are the ones you know. The claim is now about the whole procedure, interim look included.

calculated [characteristics]: meets(proposed)
  stages = (13, 30); Type I at the null rate ~ 0.0496; expected sample size under the null ~ 20.58
  power ~ 0.8002; power target met = true; Type I target met = true
verified [verification]: meets(proposed)
  The complete two-stage design (stages 13 and 30, continuing above 3 responses and
  rejecting above 12 in total) rejects with probability at most 1/20 for every
  response rate at or below 1/5.
  It rejects with probability at least 4/5 at the response rate 2/5.

Compare with lesson 9. The fixed design needed 35 participants. This one needs up to 43, but if the treatment does not work it stops after 13 about three times in four, for an average of 21.

After the study

Enter the counts as they happened. Here 5 of 13 responded in stage one, so the study continued, and 9 of 30 responded in stage two:

let data = completed_stages(analysis=proposed, stage1_responses=5, stage2_responses=9)
let outcome = verify(two_stage_result(data))
verified [outcome]: result(data)
  With 5 responses in stage one the declared rule continues, and with 14 responses
  in total it rejects the null.
  The complete design rejects with probability at most 0.0496 for every response
  rate at or below 1/5.

If the study had stopped, you would write stopped_at_interim(analysis=proposed, stage1_responses=3). Counts that contradict the rule are rejected: you cannot report stage-two data for a study the rule would have stopped.

Finding a design

You do not have to guess the numbers. Describe the search and use sample_size:

calculated [found]: sample_size(search)
  continue above 4 responses in stage one; reject above 10 in total (minimax design)
  stages = (18, 15); expected sample size under the null ~ 22.25
  power ~ 0.8011; power target met = true; Type I target met = true

"minimax" finds the design with the smallest maximum size (33 here). "optimal" finds the one with the smallest average size when the treatment does not work, which is the design we proposed by hand. Verifying a search certifies the selected design. That it is the best one is a calculation, and the output says so.

What you learned

  • An early stop is safe when it is declared as part of the design.
  • The same target and meets claim apply to the whole procedure.
  • A search finds a design; verification checks the one it found.

Try it

Replace calculate with verify on the last line, then switch the criterion to "optimal".

Lesson 11

A Bayesian stopping rule

In this lesson

Many teams prefer to decide with posterior probabilities. We write such a rule and then check its false-positive rate and power, which the rule alone does not give us.

beta_prior
The prior belief about the response rate. a=1, b=1 is uniform. Parameters are positive whole numbers.
posterior_rule
Decisions are based on the posterior probability that the response rate exceeds reference. Continue after stage one if it is at least 1/2. Declare success at the end if it is at least 19/20.

Only the rule changed. The stages, the test and the target are declared as in lesson 10.

calculated [characteristics]: meets(analysis)
  stages = (10, 20); Type I at the null rate ~ 0.0581; expected sample size under the null ~ 22.48
  power ~ 0.8059; power target met = true; Type I target met = true
verified [verification]: meets(analysis)
  The complete two-stage design (stages 10 and 20, with its posterior interim and
  final rules) rejects with probability at most 1/10 for every response rate at or below 1/5.

Look at the false-positive rate: 5.8%. Requiring 95% posterior probability does not make it 5%. A posterior threshold and a false-positive rate are different quantities, and this is why we asked for maximum_typeI=1/10. If you need 5%, raise success_at_least and check again.

One stated limit. The posterior probability is computed with a standard closed formula. That the formula equals the Beta posterior is not proved in Lean, and the certificate lists this under its assumptions.

What you learned

  • Bayesian decision rules fit the same design and target vocabulary.
  • A posterior threshold does not set the false-positive rate; check it.
  • Certificates say what was assumed as well as what was proved.

Try it

Set maximum_typeI=1/20 and verify: you get typeI_target_not_met. Then raise success_at_least to 39/40 and see what happens to the power.

Lesson 12

A continuous outcome, and a cited guarantee

In this lesson

Not every guarantee is proved in Lean. For a t-test, StatClaim checks that your study fits the test, then tells you which published guarantee you are relying on and what it assumes.

two_arm_continuous
Two arms with a measured outcome, such as blood pressure. The model fixes no distribution. Each test states the distribution it assumes.
equal_means
The null hypothesis: the two arm means are equal.
t_test, welch_test
The pooled-variance t-test and Welch's test. You declare them exactly like fisher in lesson 1.

This file needs no Lean. Check it and read the first result:

cited [checked]: typeI(analysis)
  Evidence: cited from the literature; not machine-checked; guarantee: finite-sample bound
  Method: Two-sided pooled-variance t-test (t_test, version 1)
  Null rejection probability equals 1/20 whenever mean_treatment = mean_control.
  Assumptions:
    [independent_observations] Observations are independent within and between the two arms. (assumed)
    [fixed_sample_sizes] Arm sizes are fixed before observing outcomes. (declared)
    [single_analysis] The test is run once, on the complete data. (declared)
    [normal_outcomes] Outcomes in each arm are normally distributed. (assumed)
    [equal_variances] The two arms have the same variance. (assumed)
  References:
    Student (1908). The probable error of a mean. Biometrika 6(1), 1-25.
    ...

The status is cited, not verified. StatClaim checked the fit: the null suits the test, the null and the design describe the same study, and the design is fixed. It did not check the guarantee. That comes from the references, and it holds only under the listed assumptions.

Each assumption has a name and a mark. Declared means your file states it: fixed says the sizes are set in advance and the test is run once. Assumed means nothing in the file can show it. Normal outcomes and equal variances are yours to defend.

Welch's test drops those two assumptions, at a price:

cited [approximate]: typeI(robust)
  Evidence: cited from the literature; not machine-checked; guarantee: large-sample approximation
  Method: Two-sided Welch t-test (welch_test, version 1)

Lesson 21

A test whose level follows from the randomisation

In this lesson

The t-test's guarantee rests on assumptions about the outcomes. A randomisation test's level rests only on how the trial was randomised. Declare the randomisation on the assignment, and its Type I bound is proved in Lean, for clinics as well as for participants.

randomisation="complete"
Every split of the twelve clinics into two arms of six was equally likely. It is declared on the assignment, because it is a fact about how units reached the arms. assignment(...) takes it too.
no_effect
The sharp null: treatment changes no participant's outcome. It is a stronger statement than equal means, and a different one.
randomisation_test
Compares the observed value of a statistic, such as the difference in clinic means, with its value under every other split. Because clinics were randomised, it permutes clinics.
verified [checked]: typeI(adherence)
  Evidence: proved in Lean; guarantee: finite-sample bound
  Under complete randomisation of 12 clusters, 6 treated and 6 control, the 924 possible splits are equally likely, and that uniform law is a probability law.

Lean proves one theorem for every design: when all splits are equally likely and the outcomes do not depend on the split, at most a share alpha of the splits can give a p-value at or below alpha. Many trials randomise within strata or in blocks instead. Say so, with randomisation="stratified" and strata=[stratum(control=3, treatment=3), ...], or randomisation="blocked" and block_size. Matched pairs of clinics, one of each pair treated, are blocks of two: block_size=2. The same theorem covers them all, because each stratum or block is randomised on its own; only the count of equally likely assignments changes.

Forty participants already have 137,846,528,820 splits, too many to count. Add draws=9999 and the p-value compares the observed split with 9,999 drawn at random, counting the observed one among them. Lean proves that version too, for any number of draws.

Not a test of means. Give the randomisation test equal_means(model=practice), or a t-test no_effect(model=practice), and each is refused with hypothesis_mismatch. When effects differ between participants, the two nulls ask different questions.

  • An assignment can declare that every split was equally likely.
  • A randomisation test of the sharp null is then proved, whatever the outcomes.
  • With randomised clusters, the test permutes clusters; too few clusters to reach the level are refused.

Given the exposure, the test statistic is noncentral t; power averages that over a normal exposure. So it is exact when exposure and outcome are normal, as the tests assume. R agrees to twelve decimals by numerical integration, and a simulation of raw data agrees within its error. pwr's formulas are close: Fisher's z for the correlation, and a fixed exposure for the slope, which promises a little more power.

Lesson 35

Power for a complex survey

In this lesson

A survey that samples households, strata or with weights is not a simple random sample, so it carries less, or sometimes more, information per person. The design effect says how much, and the survey tests of lesson 27 are planned with it.

design_effect=...
The variance of the estimate in this survey over its variance in a simple random sample of the same size. A clustered sample is usually above 1; a stratified one can be below. It is a planning input, often taken from an earlier round of the survey.
calculation.effective_sample_size
n over the design effect: the simple random sample with the same power.

Twelve thousand people are worth six thousand here, and give 53% power. The survey needs 23,530, twice what a simple random sample would. design_effect is taken by outcome_prevalence, odds_per_sd and slope, for rao_scott_test, survey_logistic and survey_linear; the simple-sample tests refuse it.

Clusters still count. The design effect sums up the survey for power, but the guarantee of a design-based test still needs enough sampled clusters: at least 20, as lesson 27 checked.

What you learned

  • Survey tests are planned with design_effect on the planning point.
  • Power is that of a simple random sample of n over the design effect.
  • effective_sample_size reports that size.
